# 商品編集を「保存受付 → 裏側でPOS反映」に変える計画

調査日: 2026-10-12 JST。状態: **本番反映承認済み・DB/GAS反映完了、Git/Vercel公開確認中**。新機能の有効化/実商品保存は別確認。

## 目的・利用者の操作

商品名・商品金額・商品原価を入力し、「保存」で入力内容をサーバーに受け付ける。受付確認後は編集画面を閉じ、次の商品を編集できる。POS読取り・照合・保存・結果確認は利用者の画面から切り離す。

受付時は「変更を受け付けました。POSへ反映中です」と表示し、POS保存完了を偽らない。商品一覧には対象商品だけ小さく「反映待ち」を表示する。失敗・競合は「要確認」に変え、元の入力をサーバーから確認できる。商品一覧全体に常設の説明バナーを再追加しない。

## 確認した現行実装

- `PosProductEditModal.tsx`: 初期DB値で入力できるが、`review()` はbaseline必須。確認ボタンはbaselineなし・読取り中に無効で、`startSave()` もreviewを要求する。
- `editor.server.ts`: `loadProductEditor()` と `reviewProductEditor()` がそれぞれ実POSを読む。
- `edit-preparation.server.ts`: 保存準備でも認可・DB商品照合後に実POSを読み、検証済みsnapshotから操作台帳/dispatchを登録する。
- `edit-execution.server.ts`: claim後の一度だけ送信、consume、結果照合、DB反映、結果不明の再送拒否が既にある。これらの安全条件は維持する。
- 既存 `pos_product_operations` の `prepared` はPOS内部IDと期待結果が確定している状態。未照合の入力受付に流用して架空のID/指紋を入れない。保存本文は短い有効期限があるため、処理待ちキューに古いdispatch本文を置かない。
- 現行UIの未照合 `groupId=''` と `supplierId=null` は仮の表示値。裏側反映のpatchに含めてPOSの分類/仕入先を消さない。
- Serenaメモリ一覧は空。完了済みの先行入力・通知整理は再実装せず、新たな永続受付/workerを追加する。既存未コミットファイルは対象外。

| 後続 | 分類・仕入先の安全な店舗別候補キャッシュと即時受付、商品追加/JAN訂正/削除の非同期化 |

## 受付と裏側処理

1. **永続受付**: 短いNext APIで利用者とDBのmanager権限を確認。DBから `product_id + store_id + JAN` と現在の商品値/更新情報を取得し、編集した項目のpatchと同一操作IDを専用受付表に固定する。画面に表示された編集項目の値も要求に固定し、既にDB値が変わっていれば受付を拒否する。この通信ではPOSを読まず、confirmedのproducts行も書き換えない。
2. **競合フェンス**: 同じ商品に未完了受付を複数作らない。別IDの再受付、既存未完了POS操作との衝突は明示拒否する。既存手動prepareとmaster同期のbegin/applyも受付待ちを考慮し、店舗revision/予約を受付時から束縛する。両店舗の同じJANは独立。
3. **worker**: ブラウザから独立して受付待ちを原子的に取得し、lease/工程を記録。最初の候補は既存GASに専用の時間主導workerを追加し、DBの受付を継続処理する方式。既存売上/入出庫履歴のトリガーを置き換えない。公開入口・workerの認証、原受付actorの現在の権限をDB/RPCで再確認し、利用者のCookie/JWT/POS認証情報をキューに保存しない。
4. **新鮮なPOS照合**: 店舗/JAN/内部IDを確認し、入力した項目だけをpatchする。未変更の値・画像・設定はその時点のPOS値を使う。編集対象項目の受付基準とPOS値が異なる場合は勝手に上書きせず競合として要確認にする。既に希望値の場合もPOS保存を無条件に再実行しない。
5. **保存・反映**: 新鮮なsnapshotから既存の署名付きdispatchを直前に作り、既存claim/一度だけconsume/POS保存/結果検証/冪等DB反映に接続。利用者は入力したpatchを送信前に確認・承認するが、POS照合のため画面に留まらない。
6. **復旧**: 送信前の読取り失敗は入力を保持し、同じIDの安全な工程だけ再開可能にする。workerが落ちても受付は消えない。保存開始権取得後の結果不明は、lease失効を再保存の許可にせず、読取り・確認のみへ進める。POS確認済み/DB失敗はDB反映だけ再開する。
7. **一覧表示**: 希望値は「反映待ち」とセットで表示し、確定済みproducts値/税計算/販売/在庫計算に未確認値を混入しない。成功後に確定値へ切替。失敗時に希望値を黙って戻さず、希望値と現状/理由を確認できるようにする。

受付応答が消失した場合は同じIDの受付状態を確認し、別IDで再保存しない。受付自体に失敗した場合は画面を閉じず、入力を保持する。送信後の取消を単なるキュー削除として提供しない。未送信取消は既存の証拠・権限条件と整合させる。

既存GAS実行器は内部でもPOSを読み直すため、workerからそのまま呼ぶだけでは重複した長い照合が残る。フォーム準備・consume・保存・結果検証を安全な工程に分け、同じworker内で新鮮なフォームを保持し、準備後に短いdispatch期限を開始する。確認前のフォーム変更や画像/非対象項目の保持検査を省略して高速化しない。ブラウザ待機の解消と、裏側処理自体の通信回数削減は別々に検証する。

## 実行基盤の制約

Nextの `after()` は応答後処理に使えるが、永続キューではなく実行時間上限も残る。`void fetch()` やモーダル内Promiseだけを完了保証に使わない。

GASは時間主導トリガーを毎分設定できるが、即時開始/正確な分の保証ではない。実行6分/回、consumerアカウントのトリガー合計90分/日などの上限があるため、少量ずつ処理し、空キュー時は直ちに終了する。実装はscript lockで1実行1商品、両店舗を交互に優先し、新しい通信の開始予算を5分に抑える。現在の契約/稼働量で十分か、空キュー時の通信時間も含めて有効化前に実測し、処理間隔を決める。待ち件数・worker最終実行・上限接近の管理者監視は有効化前の残件であり、今回の画面検証で完了とはしていない。不足なら基盤変更を別途相談し、長時間POS処理をNextの短い受付リクエストへ戻さない。

## 分割工程・受入テスト（テスト先行）

### A: 受付・DB基盤

- 遅い/失敗するPOSを設定しても受付はPOS呼出し0回、DB受付成功後だけacceptedを返す。
- same ID/same patchは同じ受付。same ID/different patch、別ID/same未完了商品は拒否。受付応答消失後の状態確認で二重受付なし。
- 他店productId/JAN、権限不足、無効金額、空商品名、未知patch項目はDB/API双方で拒否。RLSは店舗別managerのみ。
- 同店舗の既存prepare/masterとの競合・古いCSVの適用は受付待ちフェンスで拒否。別店舗の同JANは独立。

### B: worker・既存保存プロトコル接続

- ブラウザ離脱・再読込後も処理継続。worker並列/異常終了/lease期限切れで保存POSTが増えない。
- 受付後の権限剥奪、店舗/JAN/内部ID不一致、POS対象項目競合では保存POST0回・入力保持・要確認。
- 未入力の分類/仕入先、画像/税/その他設定、全在庫数量/棚卸し時刻を保持。
- 読取り失敗、claim前後の異常、consume応答消失、POS保存応答消失、DB反映失敗を工程ごとに検証。同じ操作IDを維持し、結果不明は再送しない。

### C: UI・公開前検証

- POS照合完了を待たず保存受付→閉じる→別商品の編集。未編集値をpatchへ含めず、受付失敗では入力/画面を保持。
- PC/390pxスマホで対象行だけの状態表示、再表示、キーボード/カメラ等既存の商品機能に回帰なし。
- 関連テスト、全回帰、独立型検査、対象Lint、本番build。既存失敗は修正成果と分けて報告。
- 本番DB差分と論理退避、GASの既存全ソース保持、worker設定/トリガー、Git/Vercel Productionを別承認後に段階反映。実保存検証の商品/変更値は別途指定・承認を得る。
