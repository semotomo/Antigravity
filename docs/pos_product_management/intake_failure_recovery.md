# 保存受付の診断・入力復旧（2026-10-13）

本人の「お願い」で実装とGit/Vercel反映を承認。DB本番適用・GAS公開・実商品の再保存は別承認。

## 第1段階

- 受付失敗を入力/保全/通信/応答/origin/認可/DB/返値の固定コードで区別する。元例外・応答本文・鍵・入力値は診断へ出さない。DBログは限定したSQLSTATE/RESTコードだけ。
- 「受付状態を確認」はGETだけ。受付なしを正しく確認した場合の「同じ内容で再受付」だけ、同じ操作ID・希望値・表示元基準値をGET再確認後に送る。入力/IDを変更・削除しない。
- ACK消失、受付済み、別店舗/JAN/商品、偽の受付なしコードでは新規保存やID再生成を行わない。受付確認後だけ保全解除・画面を閉じる。
- 調査時は本番受付/監査/未完了操作0。本店7/JAN4969735300013の商品7145は売価1600/原価800、商品/棚卸し全列hash不変。受付失敗の原因をこの時点で断定・解決済みとはしていない。
- 関連76/76、型、対象Lint成功。全回帰624/627で既知の棚卸しsource契約2件・Sentry/CMS秘密名検査1件のみ失敗。ローカルbuildは検証用公開設定を使い、実本番設定のbuildと画面は公開後に別確認する。

## 第2段階（分類・仕入先）

- POSの完全な候補と対象商品の現在選択を、店舗+商品+JANに固定した変更不能snapshotへ保持する。CSVに仕入先は含まれないため、DBのnullからPOS未設定を推測しない。
- 分類/仕入先付き受付はsnapshotのID/名称/現在選択を固定し、workerの新鮮なPOS読取りで再照合する。未知候補、同名の別ID、改名/ID再利用、店舗混線は保存前に停止する。
- 候補取得は通常の名称/価格受付を止めずに準備する。冷キャッシュでは最初の候補読取りが必要であり、商品一覧の名前だけを完全なPOS候補として代用しない。
- DB migrationとGAS worker拡張の本番適用が必要。既存のconsume、結果不明時の再送拒否、画像/未編集属性保持を維持し、別承認前はこの拡張を有効化しない。
