## 3. 入力仕様

### 商品編集（最初に提供）

1. 権限のある店舗を一つ選び、JANで検索。全店舗表示のまま保存しない。
2. POSの店舗フィルタ＋商品コード/メーカー品番の**完全一致**から候補を取得し、内部商品IDを特定する。
3. 複数候補、商品コードとメーカー品番が別商品に一致、両店共有所属、所属不明、店販以外の場合は自動選択・保存を拒否し理由を表示。
4. 商品名、商品グループ、商品金額、商品原価、仕入先を編集。通常編集では店舗・JAN・内部商品IDを固定。JAN訂正は下記の専用操作、店舗移管は対象外。
5. 最新POS詳細と編集開始時の値を比較し、外部編集があれば競合として停止。保存前に変更項目だけを確認表示する。
6. POSの編集・保存・確認に相当する送信を実行し、完了画面だけでなく再取得した値の一致まで確認する。
7. POS確認後に同店舗のSupabase商品へ反映し、「POS保存・ダッシュボード反映完了」と表示する。

既存の原価を自動で半額へ戻さない。非対象フィールド（フリガナ・略称・税・ポイント・価格方式等）は既存値を保持。
「会計時に入力」や店舗別価格の既存商品を、通常編集で意図せず固定金額/一括価格に変換しない。対応範囲は実フォーム確認後に確定する。

### 商品追加（編集完成後）

操作順: 商品追加 → **店販 → 所属店舗グループ** → 商品グループ → その他の入力 → 差分確認 → 保存。

| 項目 | 仕様 |
|---|---|
| 店舗 | 本店7またはわんわん6。POS所属は許可された一店舗のみ。全店を送らない |
| 区分 | 店販固定。選択後に最新フォーム/選択肢を再取得する |
| 商品名 | 必須。将来のJAN検索は候補提示だけの入力補助 |
| 商品グループ | 対象店舗・店販のPOS選択肢を表示し、名称ではなくIDで送信 |
| JAN | 文字列で保持し先頭0を保護。商品コード・メーカー品番の両方へ同一値を送信 |
| 商品金額 | POSと同じ金額単位。設定範囲は一括、固定金額を使用 |
| 商品原価 | 初期値は商品金額×0.5の1円未満切り捨て。自動設定中は金額変更に追従、手入力後は上書きしない |
| 仕入先 | 判明していればPOSの選択肢から選択。不明は未設定、名前から推測して確定しない |
| 不使用 | 商品コード自動発行、商品名フリガナ、商品略称は表示・使用しない |

店販/所属変更で選択肢や価格が初期化されることを前提に、変更後のフォーム状態を取得してから値を入れる。
入力後に店舗を切り替えた場合は利用者へ警告し、古い店舗のグループ/仕入先IDを送信しない。
2026-09-09: POS追加フォームで原価499.5円がフォーカス離脱時に499円になることを未保存で確認。ユーザーが切り捨てを承認したため、自動原価は1円未満切り捨て（売価999円→原価499円）とする。手入力・既存原価は自動上書きしない。POS保存時の金額制約は別途検証する。
JAN長・金額上限・名前の長さ/文字コードは現行POSの制約を確認してから確定する。

### JAN訂正・商品削除（追加承認 2026-09-08）

- JAN訂正: 店舗・商品内部IDは保持し、商品コード/メーカー品番を同じ新JANへ更新。旧JAN/新JAN、理由、実行者、時刻を監査に残す。同店舗の既存JANや過去JANとの衝突を拒否し、別商品との自動統合はしない。
- 通常編集からJANを変更できる現行経路を、新しい訂正機能公開時に閉じる。旧JANによる売上・移動・棚卸しが引き続き元の商品へ解決されることを必須とする。
- 棚卸し明細の `jan_snapshot` は変更しない。現在は `products.jan_code` への複合FKがあるため、過去JANの同店舗対応表を含むDB設計/再集計変更と検証が済むまでは参照のある商品のJAN訂正を拒否する。
- 商品削除: 停止と削除を混同しない。POSの削除機能・制限を実画面で確認して提供する。売上/棚卸し/移動/客注/現在庫等への参照がある商品は物理削除を拒否し、既存の理由付き停止を案内する。POS側参照の有無も確認できない場合は削除を許可しない。
- 削除時は店舗名・商品名・JAN・理由・明示確認を必須とし、取得済み詳細の指紋と最新状態を比較。実削除後も操作監査とJAN予約（再利用による履歴混同防止）を残す。
- 保存/訂正/削除の途中結果不明は再送せず同一操作を再照会する。削除確認の際の「検索0件」だけを成功証明にしない（ログイン失効/検索失敗を区別）。

## 4. 書込み・復旧の構成案

`入力保持 → 店舗管理者認可 → POS対象/最新値の確認 → 操作受付 → POS保存 → POS再照合 → 同店舗DB反映`

- POS連携は既存GASのログイン・店舗選択を再利用するHTTPフォームアダプターを第一候補とする。正式APIの有無/利用条件も確認する。画像だけでhidden値や保存ボタン名を推測して実装しない。
- 既存の読み取りhelperを、書込みに必要な厳格なフォーム契約（許可ホスト、action、区分、所属、必須hiddenの存在）と照合する。想定外の画面、ログイン失効、確認文の変化で保存を停止する。
- Server Action/APIのすべてで `auth.getUser()` と `user_store_access` の対象店舗managerを確認。画面cookieや送信store_idだけを信用しない。POS側にも許可された店舗対応を持ち、入力URLや任意の資格情報を受け付けない。
- GASへの商品用通信は署名付きPOSTとし、操作ID・利用者・店舗・内容hash・期限を束縛する。専用秘密鍵はサーバー環境/Script Propertiesで保持し、ブラウザへ渡さない。GETで商品保存を実行しない。
- DBの操作claimを原子的に行い、一操作一送信に制限する。二重クリック/二重配送では同一操作の状態を返す。POSに冪等キーが無い場合は「exactly once」を保証できると説明しない。
- 送信後に応答が途切れた場合は「結果確認中/要確認」にする。自動再送せず、同店舗JAN・内部ID・内容で確認する。作成候補が複数なら人が確認する。
- POS成功/DB失敗は別状態として保存し、POS再保存ではなくDB反映だけを再実行する。DB保存済みだけでPOS成功と表示しない。
- フォームは状態確認中も閉じず、入力値・操作IDを保持する。通信エラー/別端末競合で空欄や旧値へ戻さない。店舗変更・画面離脱・保存中の再操作には保護を付ける。
- 変更中の商品を古いCSV同期で上書きしない。同じ店舗/JANの書込みと既存GAS同期を共通の競合制御に参加させ、同期取得開始時刻/版と操作状態を確認する。古い全件CSVによる追加商品の停止/所属整理にも同じ保護を適用する。
- 商品更新は棚卸しの数量・計数時刻・現在庫・販売履歴snapshotを変更しない。手動停止状態・ブランド等のローカル専用情報を保護する。
- 商品名変更で名前依存の売上照合が切れないか確認し、必要なら同店舗の旧名称aliasを競合チェック後に保護する。既存aliasを別商品へ無断変更しない。

### DB案（DDL・本番適用は未実施）

| テーブル案 | 主な内容・制約 |
|---|---|
| `pos_product_links` | product_id/store_id/JAN、POS会社・内部商品ID、所属グループ、最終確認hash/時刻。既存商品の複合FK。書込み可能な同一POS実体を両店へ割り当てない制約 |
| `pos_product_operations` | UUID操作ID、create/update、利用者/店舗/JAN、変更前後の対象値、payload hash、期待版、状態/結果。操作ID＋内容一致、対象商品同時実行制約、機密を含まないエラー分類 |
| `pos_product_operation_events` | append-only監査。誰が・いつ・どの店舗/商品へ・どの変更/状態遷移を行ったか。復旧操作も追記 |

候補状態: `prepared → dispatching → verifying → pos_confirmed → completed`。
`rejected`（未送信）、`uncertain`（送信有無/結果不明）、`db_pending`（POS確認済み・DB未反映）を区別する。
作成時はproduct_idがまだ無いので店舗/JANで操作を受け付け、POS再照合後のtransactionでproducts・link・完了状態を整合させる。
直接書換えを禁止し、RLS/制限付きRPCで対象店舗managerの操作に限定。service role利用時もRPCで対象・依頼者・許可フィールドを検証する。
既存productsのRLS/GRANTとGAS同期資格情報は本番の読み取り監査が必要。匿名経路や従来Actionで迂回できるまま公開しない。
RLS変更は既存の検索・客注・移動・棚卸し・自動同期に影響するため、正確な対象と移行手順を別途レビューし承認後に適用する。

- 作成直前のPOS＋DB重複確認、作成結果不明時の再照合、追加後の通常同期/棚卸し検索をテスト。
- 実POSでの追加は対象JAN・店舗・名前・金額・原価・グループをユーザー確認してから行う。

### P4: 検証と段階公開

- 正式回帰 `node --test tests/*_test.mjs`、型検査、対象Lint、全体Lint、本番build。既存違反と新規違反を分けて報告する。
- PC/スマホのJAN検索・入力・取消・保存失敗・店舗分離、ユーザー指定の商品で実POS保存、通常同期後の値保持を確認。
- 棚卸し/現在庫/確定後同期/印刷CSV/売上推移/客注/店舗間移動が維持されることを回帰確認。
- DB・GAS・Git・Vercelは差分/バックアップ/復旧手順を提示し、それぞれ承認済み対象だけ反映。新旧プロトコル互換とfeature flagによる段階有効化を用意する。
- Production Readyだけで完了とせず、公開URLで認証・対象店舗・保存/再同期を確認。実機未確認を明示する。

## 6. 先行する受入テスト

外部書込み・認可・金額計算を含むためTDDを採用する。実装前に以下の期待結果を確認する。

| ケース | 期待結果 |
|---|---|
| 同一JANが両店舗にある | 選択店舗のPOS内部商品だけ変更し、他店のPOS/DBは不変 |
| store6専用利用者がstore7/API/operation IDを指定 | 読取り/書込み/状態参照を拒否し、POSリクエスト0回 |
| POS候補0件、複数、共有所属、コードとメーカー品番の不一致 | 自動更新・自動追加しない。原因を表示 |
| 作成1000円/原価未編集 | 原価500円。手入力450円後に売価変更しても450円を保持 |
| 999円の50%、0円、未入力、負数、上限、先頭0のJAN | 999円→499円、0円→0円。未入力と0を区別し、不正入力を拒否。手入力原価は保持 |
| 店販/所属変更でフォーム/選択肢が変わる | 最新状態に値を入れ、旧hidden/他店optionを送信しない |
| 保存二重クリック/同一操作の二重配送 | POSへの変更送信は同一操作で最大1回、同じ結果を返す |
| POS送信直後の切断/期限切れ/プロセス停止 | 入力保持、結果不明表示、状態確認。自動の新規再送なし |
| POS成功・Supabase失敗 | POS成功を区別表示し、DB反映のみ再試行。二重作成なし |
| 他担当が先にPOS編集/同じ商品を別端末で編集中 | 期待版不一致として保存拒否。入力を保持して差分を表示 |
| 定期同期が古いCSVを取得後に商品保存/作成 | 古い値への巻戻り・追加商品の誤停止/所属整理を防止 |
| 既存フリガナ/略称/停止/税/ブランドあり | 対象外の値を保持。棚卸し数量と時刻は変えない |
| 商品名変更と旧名称の販売履歴 | 同店舗の紐付け維持、他店aliasは不変 |
| 確認文・form構造・ログイン状態が想定外 | フェイルクローズ。保存成功と表示しない |

### 追加受入テスト

- JAN訂正: 他店に同JANは許可、同店舗の現行/旧JAN衝突は拒否。理由・旧JAN一致・同一POS内部IDを必須とする。
- JAN訂正: 棚卸しsnapshot・数量・時刻は不変。旧JAN販売を取りこぼさず、旧新JANの同じ販売を重複加算しない。
- 削除: 参照/現在庫/未完了操作がある、または調査不能ならPOS削除送信0回。チェック後に参照が追加される競合もDBで拒否する。
- 削除: 別店舗の同一JAN、操作監査、過去の数量/売上/移動/客注データは不変。停止を削除成功として表示しない。

## 7. 次の確認事項

- 実装計画は承認済み。管理者権限のある店舗だけを対象にし、JAN訂正・商品削除も安全条件を満たす場合に実装する。
- 両店の商品詳細/編集と追加フォームの動的候補は確認済み。次は安定した内部IDと、全保存項目の保持・保存結果の取得契約を確定する。ユーザーは保存済み情報によるログイン操作を承認済み。資格情報を読み出したり記録したりしない。
- 原価初期値の切り捨ては2026-09-09に承認済み。価格の保存制約・実保存対象商品は別途確認し、共有商品の一括変更や本番データ作成を先回りしない。
